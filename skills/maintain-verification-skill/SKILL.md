# Maintain a verification skill

A feature map rots as soon as the project changes. This skill is the upkeep pass for a skill generated by `/create-verification-skill` (or any project-local verification skill with a feature map). The unit of rigor is the feature, not every individual sentence: cover every feature file from source and exercise every feature live, without turning every bullet into an isolated test run.

## Outcomes

Pick one outcome and state it clearly:

- **clean:** Every feature got source and live coverage, with nothing worth shipping. No branch, no PR.
- **changed:** Proven documentation, driver, or feature-map corrections are ready (ask before pushing or opening a PR unless the user explicitly requested one).
- **blocked:** Coverage could not finish or a proven fix could not ship safely. State the exact blocker.

## Edit scope

Only edit the verification skill's own directory (`SKILL.md`, `features/`, and any helper scripts it owns). Never edit product code during a maintenance pass. When the app no longer behaves as the feature map describes, it is either documentation drift (update the map) or a product regression (report it clearly without hiding it in docs).

## Pass

### 0. Locate the target

Find the project-local verification skill whose body has Launch and Drive sections and a feature map (usually `verify-*/` in `.agents/skills/`, `.github/skills/`, `.claude/skills/`, or `.cursor/skills/`).

- If several candidates exist, ask the user which one to maintain.
- If none exist, stop and point the user to `/create-verification-skill` instead of inventing a target.

### 1. Index hygiene

Read the feature map `README.md` and list its sibling feature files. Fix missing, extra, duplicate, or dead entries. Keep this lightweight with no generated inventory boilerplate.

### 2. Source wave

Read [`../develop/references/config-and-subagents.md`](../develop/references/config-and-subagents.md) and resolve `low_effort_model` (default `inherit`), `delegation_policy`, and `parallel_subagents` (default `2`) from `develop-config.md`.

- When `delegation_policy` is not `single-agent` and your coding assistant has a subagent tool, launch read-only source-reader subagents in batches of at most `parallel_subagents` concurrent subagents (do not exceed `parallel_subagents` without asking the user first). Start every subagent kickoff with `Read <develop-dir>/worker.md before anything else.` and apply the deprecated-model fallback protocol if a configured model is rejected.
- Otherwise scan feature files sequentially in the main session.
- Each reader answers "how does this user-facing feature work?" from source, flags likely documentation drift with file citations, and returns one concise live-verification recipe. Readers never drive the app and never edit files.
- Return shape per feature: feature summary, source entry points, likely drift (or none), and one verification recipe.

### 3. Reconcile

Confirm every feature file has a summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift without re-proving clean claims. Check recent repository changes for user-facing entry points missing from the map, requiring a concrete source path before flagging a feature as missing.

### 4. Live pass

Run the live pass even when source review looks clean. The main session owns all live driving. Follow the verification skill's own Launch model (one long-lived instance driven serially for servers and GUIs, or a fresh isolated session per run for short-lived CLIs and libraries).

Exercise every mapped feature at least once while keeping three invariants throughout the pass:

1. **Health-check before driving.** Never drive an instance you have not health-checked since it last behaved unexpectedly. Run `doctor` before the first drive, on each fresh session, and again after any failed drive. When `doctor` cannot see a wedged UI state on a healthy process, reset to a known state or relaunch instead of guessing.
2. **Preserve proof artifacts.** Verify that captured evidence survives every cleanup at its named path rather than assuming it survived.
3. **Clean all temporary residue.** Nothing a drive started may outlive that drive's usefulness. Clean up failed-iteration residue whether the session is stuck, exited, or shared (on a shared instance, clean only the residue, not the shared instance).

Additional rules during the live pass:

- If `doctor` fails because the verification skill drifted, fix the skill within edit scope, restart only what the fix invalidated, and retry once before declaring `blocked`.
- Mark a feature `verified-unreachable` only with the concrete unmet prerequisite (auth, license, OS, or external state) and the exact route attempted. If the map omits that prerequisite, fix the map as drift.
- Re-drive any driver or helper fix live before shipping it.
- Run final teardown after the last drive (including re-proofs) so no processes or temp state outlive the run, while keeping proof artifacts intact.

### 5. Triage

- **Wrong or missing user-POV description:** documentation drift. Fix it in the feature map.
- **Working behavior the verification driver cannot exercise:** driver gap. Fix it following the helpers rule (scripts executable, invocation documented in `SKILL.md`).
- **Broken product behavior:** product regression. Report it clearly to the user and keep it out of this change.

### 6. Report and confirm before shipping

- For **changed:** Re-read every changed file, summarize the verified fixes, and keep edits local unless the user explicitly asked for a pull request (ask before pushing a branch or opening a PR).
- For **clean** or **blocked:** Create no branch or PR. Report the outcome and exact feature coverage honestly.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; do not commit them.
